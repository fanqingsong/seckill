# 第 1 课：系统全貌

本课不打开 Java 文件。先建立地图，后面每一课只填地图上的一块。

## 这个项目在解决什么

秒杀时很多人同时抢少量券。如果每一次抢券都同步写数据库，数据库会先被打满。

这个项目把「抢」和「记下来」拆开：

1. 抢的瞬间只跟 Redis 打交道，尽快告诉用户成功或失败。
2. 成功记录先放进 Redis 队列，再由后台写入 PostgreSQL。
3. PostgreSQL 里的事件通过 Kafka 送给另一个服务，更新「给查询用的数据」。
4. 页面上的活动列表和我的券，读的是这份查询数据，不是抢券当时那张表。

这种拆法有两个名字，先记住含义即可：

- **CQRS**：写请求和读请求走不同的服务。写走 Command，读走 Query。
- **事件溯源**：PostgreSQL 里按顺序追加「发生过什么」（活动开始、某人抢到、活动结束），而不是只改一行「剩余库存」。

## 进程各自干什么

| 名字 | 端口 | 一句话 |
|------|------|--------|
| 前端 nginx | 8080 | 提供页面，并把 `/admin`、`/command`、`/query` 转给 Gateway |
| Gateway | 8085 | 按路径转发，并做限流、熔断 |
| Admin | 8081 | 创建、修改活动，写入 PostgreSQL |
| Command | 8082 | 到点初始化库存，处理抢券 |
| Query | 8083 | 查询正在进行的活动和某人的券 |
| Event | 8084 | 消费 Kafka，更新查询用的数据；回放也在这里 |

旁边还有四个基础设施，浏览器不直接访问它们：

| 名字 | 作用 |
|------|------|
| PostgreSQL | 活动表、事件表、待发送消息表（outbox） |
| Redis | 库存和抢券热路径；查询用的读模型；生产环境 Gateway 的限流计数。Compose 下开 AOF 并挂数据卷 |
| Kafka | 把已提交的事件从 Command 送到 Event |
| Elasticsearch | 券和活动的搜索索引。普通列表查询仍走 Redis |

## 三条用户操作

**创建活动**

浏览器 → nginx → Gateway → Admin → PostgreSQL。  
此时 Redis 里还没有库存。Command 里有一个定时任务，等到 `publishTime` 才初始化 Redis，并写下「活动开始」事件。

**抢券**

浏览器 → nginx → Gateway → Command → Redis。  
Redis 接受后，HTTP 就返回 `Request accepted`。写入 PostgreSQL、发 Kafka、更新查询结果都发生在这个响应之后。

**查询**

浏览器 → nginx → Gateway → Query → Redis（搜索接口才走 Elasticsearch）。  
所以刚抢成功时，查询页可能还看不到券。那是正常的延迟，不是抢失败。

## 三种事件

后面读代码时会反复看到这三个名字：

| 事件 | 含义 |
|------|------|
| `PromotionStartEvent` | 活动开始，Redis 库存已初始化 |
| `CouponGrabbedEvent` | 某个用户抢到一张券 |
| `PromotionFinishEvent` | 活动结束（库存卖完，或到了结束时间且抢券队列已空） |
