## 工人线程

`GrabPersistWorker` 不是单独的进程，也没有自己的容器。它带有 `@Component`，跑在 Command 服务同一个 Java 进程里。构造方法用 `Executors.newSingleThreadScheduledExecutor()` 再开一条线程，每 50 毫秒跑一次 `drain`，一批最多处理 50 条。Command 停掉时，这条线程一起停。

`drainOne` 的顺序：

1. `store.pollInflight()` 从 `seckill:grabs` 取出令牌，并放进 `seckill:grabs:inflight`。  
   先放进 inflight，是为了进程在写数据库途中崩溃时，这条令牌还在，重启后可以继续。
2. 用令牌上的 `promotionId` 找到对应的 `SecKillCommandService`。
3. 调用 `persistGrab`。如果数据库唯一约束认为这是重复券，当成已经成功，把 inflight 里的令牌删掉。
4. 其他写入失败则把令牌放回队列稍后再试。
5. 这张券刚好是最后一张库存时，调用 `finish`，再写一条 `PromotionFinishEvent`。

## 同一次数据库事务里写两行

架构图里的「same TX event plus outbox」就是 `TransactionalEventOutboxWriter.persist`。`persistGrab` 把抢券事实包成 `CouponGrabbedEvent`，再调用它。活动结束时的 `finish` 也走这个方法，写入的是 `PromotionFinishEvent`。

`@Transactional` 包住下面两次 `save`：事件表和 outbox 表要么一起提交，要么一起回滚。

一次事务里有两样东西：

- **事件表**：已经发生的事实，追加，不修改旧行。
- **outbox 表**：一条「待发送」记录，内容和事件对应。

事务提交之后，这件事才算在 PostgreSQL 里成立。发送 Kafka 不放在抢券的 HTTP 线程里，也不放在这个事务里面直接发。如果先发 Kafka 再提交数据库，可能出现消息已发出、数据库却回滚的情况。

## OutboxRelay 负责发出去

`OutboxRelay` 读取已提交、尚未发送的 outbox 行，发到 Kafka 主题 `seckill.events`。消息的 key 是 `promotionId`，因此同一活动的事件在同一个分区里保持顺序。发送成功后把 outbox 行标成已发送。

到这里，Command 的工作结束。谁来消费这条消息，是第 8 课的 Event 服务。
