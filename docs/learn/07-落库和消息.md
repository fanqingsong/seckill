## 工人线程

`GrabPersistWorker` 跑在独立的 Persist 服务里（端口 8086），不在 Command 进程中。它用 `XREADGROUP` 阻塞读取 `seckill:grabs` 消费组 `persist`，空队列最多等 1 秒。Persist 停掉时，这条线程一起停。Command 只负责扣库存和 `XADD`。

`drainOne` 的顺序：

1. `store.pollInflight()` 用 `XREADGROUP` 取令牌。先读本消费者尚未 `XACK` 的消息，大约每 5 秒才 `XAUTOCLAIM` 一次（认领空闲超过 30 秒的消息），然后阻塞等待新消息。消息留在 pending，进程在写数据库途中崩溃后可以继续。
2. 用令牌上的 `promotionId` 读取活动。同一场活动第一次查 PostgreSQL，之后用进程内缓存。活动开始后 Admin 不再允许改这一行。找不到则 `XADD` 一条新消息并 `XACK` 旧的，稍后再试，并且不写入缓存。
3. 把抢券事实写成 `CouponGrabbedEvent`。如果数据库唯一约束认为这是重复券，当成已经成功，`XACK` 并 `XDEL`。
4. 其他写入失败则不确认，这条消息留在 pending，稍后再试。
5. 这张券刚好是最后一张库存时，用活动编号加类型询问有没有 `PromotionFinishEvent`，不再把该活动全部抢券行装进内存。还没有的话再写一条结束事件。

## 同一次数据库事务里写两行

架构图里的「same TX event plus outbox」在 Persist 服务里是 `PersistOutboxWriter.persist`。抢券事实包成 `CouponGrabbedEvent` 后调用它。活动结束时写入的是 `PromotionFinishEvent`。Command 里的 `TransactionalEventOutboxWriter` 仍负责活动开始，以及到点结束时的同一张表。

`@Transactional` 包住下面两次 `save`：事件表和 outbox 表要么一起提交，要么一起回滚。

事件表在 `(promotionId, type)` 和 `(promotionId, seq)` 上有索引，outbox 在 `(published, id)` 上有索引。列没有变，只是让「有没有结束事件」「按序号回放」「取未发布的前 50 行」不必扫全表。活动表的 `promotionId` 同样有索引。

一次事务里有两样东西：

- **事件表**：已经发生的事实，追加，不修改旧行。
- **outbox 表**：一条「待发送」记录，内容和事件对应。

事务提交之后，这件事才算在 PostgreSQL 里成立。发送 Kafka 不放在抢券的 HTTP 线程里，也不放在这个事务里面直接发。如果先发 Kafka 再提交数据库，可能出现消息已发出、数据库却回滚的情况。

## OutboxRelay 负责发出去

`OutboxRelay` 读取已提交、尚未发送的 outbox 行，发到 Kafka 主题 `seckill.events`。消息的 key 是 `promotionId`，因此同一活动的事件在同一个分区里保持顺序。发送成功后把 outbox 行标成已发送。

到这里，Command 的工作结束。谁来消费这条消息，是第 8 课的 Event 服务。
