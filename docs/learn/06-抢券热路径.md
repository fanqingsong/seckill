## 活动要先「挂」进内存

Controller 不自己创建抢券逻辑。它拿着一个 `Map<String, SecKillCommandService<String>>`，键是 `promotionId`。

这个 Map 由 Bootstrap 在活动开始时放进去。所以：

- 活动还没到 `publishTime`：Map 里没有这个 id，接口返回 **400**，原因是无效活动。
- 活动已开始：Map 里有对应的 `SecKillCommandService`，才会去 Redis 抢。

## `addCouponTo` 的三个结果

`SecKillGrabResult` 只有三种，Controller 把它们变成 HTTP：

| 结果 | HTTP | 正文含义 |
|------|------|----------|
| `Success` | 200 | `Request accepted` |
| `Failed` | 429 | 售罄，或活动已结束 |
| `Duplicate` | 429 | 这个用户已经抢过 |

`addCouponTo` 里真正的判断只有几行：活动已结束则失败；否则调用 `store.tryGrab`；再按 Lua 的返回值映射成上面三种。

## Redis 里一次抢券改了什么

`JedisSecKillStore.tryGrab` 执行一段 Lua。Lua 在 Redis 里原子执行，库存检查和扣减不会被另一次抢券插队。涉及的键：

| 键 | 作用 |
|----|------|
| `seckill:stock:{promotionId}` | 剩余库存 |
| `seckill:claimed:{promotionId}` | 已经抢到的用户集合，用来挡重复 |
| `seckill:seq:{promotionId}` | 这条活动上的事件序号 |
| `seckill:grabs` | 待落库的抢券令牌队列 |

成功时 Lua 会把一枚令牌 `RPUSH` 进 `seckill:grabs`。HTTP 线程到这里就返回了，它不等待 PostgreSQL。
