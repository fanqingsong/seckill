# 第 6 课：抢券热路径

本课只跟到 HTTP 返回为止。写入 PostgreSQL 的后台线程留到第 7 课。

热路径就是用户点击「抢券」之后、到 HTTP 返回之前必须立刻跑完的那段代码。很多人会同时打到它，所以它只跟 Redis 打交道：

```text
浏览器 → nginx → Gateway → Command → Redis Lua
                                      ↓
                              立刻返回 200 或 429
```

写 PostgreSQL、发 Kafka、更新查询结果都发生在返回之后，那些是冷路径。

1. `service/seckill-command-service/src/main/java/io/servicecomb/poc/demo/seckill/SecKillPromotionBootstrap.java`  
   只看 `run` 方法在「时间到了」时做哪两件事：初始化 Redis、写下活动开始事件。
2. `service/seckill-command-service/src/main/java/io/servicecomb/poc/demo/seckill/web/SecKillCommandRestController.java`
3. `service/seckill-command-service/src/main/java/io/servicecomb/poc/demo/seckill/SecKillCommandService.java`  
   只看 `addCouponTo`。
4. `library/seckill-infra-redis/src/main/java/io/servicecomb/poc/demo/seckill/redis/JedisSecKillStore.java`  
   只看 `tryGrab` 以及文件后面的 `stockKey`、`claimedKey`。

## 活动要先「挂」进内存

Controller 不自己创建抢券逻辑。它拿着一个 `Map<String, SecKillCommandService<String>>`，键是 `promotionId`。

这个 Map 由 Bootstrap 在活动开始时放进去。所以：

- 活动还没到 `publishTime`：Map 里没有这个 id，接口返回 **400**，原因是无效活动。
- 活动已开始：Map 里有对应的 `SecKillCommandService`，才会去 Redis 抢。

## `addCouponTo` 的三个结果

`SecKillGrabResult` 只有三种，Controller 把它们变成 HTTP：

| 结果 | HTTP | 正文含义 |
|------|------|----------|
| `Success` | 200 | `Request accepted` |
| `Failed` | 429 | 售罄，或活动已结束 |
| `Duplicate` | 429 | 这个用户已经抢过 |

`addCouponTo` 里真正的判断只有几行：活动已结束则失败；否则调用 `store.tryGrab`；再按 Lua 的返回值映射成上面三种。

## Redis 里一次抢券改了什么

`JedisSecKillStore.tryGrab` 执行一段 Lua。Lua 在 Redis 里原子执行，库存检查和扣减不会被另一次抢券插队。涉及的键：

| 键 | 作用 |
|----|------|
| `seckill:stock:{promotionId}` | 剩余库存 |
| `seckill:claimed:{promotionId}` | 已经抢到的用户集合，用来挡重复 |
| `seckill:seq:{promotionId}` | 这条活动上的事件序号 |
| `seckill:grabs` | 待落库的抢券令牌流 |

成功时 Lua 会把一枚令牌 `XADD` 进 `seckill:grabs`。HTTP 线程到这里就返回了，它不等待 PostgreSQL。

架构图里的「Redis Lua stock plus grab queue」不是另一个进程。它就是这里的 Redis：库存和抢券队列放在一起，由 `JedisSecKillStore` 里的 `GRAB_LUA` 一次改完。Redis 从 2.6 起在服务器进程里内置了 Lua，`jedis.eval(GRAB_LUA, ...)` 就是把脚本交给 Redis 执行。脚本执行期间，Redis 不会插入别的命令。

调用链就这三处，没有单独的配置开关：

1. `SecKillCommandRestController.seckill` 接收 `POST /command/coupons/`，调用 `addCouponTo`，把结果变成 200 或 429。
2. `SecKillCommandService.addCouponTo` 先看活动是否已结束，再调用 `store.tryGrab`。
3. `JedisSecKillStore.tryGrab` 执行 `GRAB_LUA`。

## 这几个键的类型

Redis 没有单独的整数类型。一个键只能是字符串、列表、集合、有序集合、哈希这几类。数字也放在字符串里，内容是十进制文本，例如 `"100"`。`INCR` 和 `DECR` 会把这段文本按整数加减，再写回字符串，所以库存类型一直是 string。Lua 里的 `tonumber(...)` 是为了拿它和 `0` 比较。

| 键 | Redis 类型 | 里面放什么 |
|----|------------|------------|
| `seckill:stock:{活动ID}` | string | 剩余库存，例如 `"97"`。`DECR` 减 1 |
| `seckill:seq:{活动ID}` | string | 事件序号，例如 `"3"`。`INCR` 加 1 |
| `seckill:claimed:{活动ID}` | set | 已经抢到的 `customerId`。成员不重复 |
| `seckill:grabs` | stream | 待落库令牌。字段 `payload`，消费组 `persist` |

`seckill:grabs` 里一条令牌的 `payload` 用制表符拼起来，`GrabToken.parse` 再拆开：

```text
活动ID \t 用户ID \t 序号 \t 扣完后的剩余库存
```

例如 `活动A\tzhangsan\t3\t97`。
