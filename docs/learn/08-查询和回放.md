## 三本记录各答一种问题

PostgreSQL 是账本：谁在什么时候抢到了券，按顺序记在事件表里，这是最终依据。

Redis 是按已知键就能直接取到的数据。抢券要马上知道还剩几张、这个人抢过没有，所以库存和已抢用户在 Redis。页面上「正在进行的活动」和「某人的券」也是拿着活动 ID 或用户 ID 去取，同样读 Redis。

Elasticsearch 只接搜索。`GET /query/coupons/search` 的 `customerId`、`promotionId` 都可以不传，这种按字段组合过滤不适合用一个 Redis 键定位，所以 Event 服务另外投影一份到 Elasticsearch。

普通查询不能改成只读 Elasticsearch。`GET /query/promotions` 和 `GET /query/coupons/{customerId}` 读的是 Redis。抢券热路径也离不开 Redis。

## Event 服务处理哪三类事件

Kafka 把 `seckill.events` 交给 `EventProjector.onEvent`，`apply` 只认这三类。每类成功投影后，还会把 `seckill:applied_seq:{活动ID}` 写成这个事件的序号。下面的 JSON 是按字段举的例子，时间是毫秒时间戳。

### PromotionStartEvent

Redis 写入哈希 `seckill:active_promotions`，字段名是活动 ID，值是活动 JSON。Elasticsearch 的文档地址是 `/seckill-promotions/_doc/{活动ID}`，正文相同。

```json
{
  "id": 1,
  "promotionId": "活动A",
  "publishTime": 1758672000000,
  "finishTime": 1758675600000,
  "numberOfCoupons": 100,
  "discount": 0.8
}
```

### CouponGrabbedEvent

Redis 记三个地方：

```text
seckill:coupon:活动A:zhangsan          string，值是下面的 JSON
seckill:customer_coupons:zhangsan     set，成员 "活动A:zhangsan"
seckill:coupons_by_id                 zset，分数是券 id，成员是同一段 JSON
```

```json
{
  "id": 15,
  "promotionId": "活动A",
  "time": 1758672012345,
  "discount": 0.8,
  "customerId": "zhangsan"
}
```

Elasticsearch 的文档地址是 `/seckill-coupons/_doc/活动A:zhangsan`，正文是同一段 JSON。文档编号已经包含活动和用户，再写一次会覆盖这一份。

### PromotionFinishEvent

Redis 执行 `HDEL seckill:active_promotions 活动A`，把活动从正在进行的列表里去掉。

Elasticsearch 不删文档，只给原活动文档补上 `"finished": true`。开始时的字段还在。

## 读和写怎样对齐

Event 服务不保证查询和 PostgreSQL 在同一时刻一致。抢券的 200 只表示 Redis 库存已经扣减。查询看到这张券，要等工人线程落库、outbox 发到 Kafka、投影写完读模型。

`EventProjector.project` 用 `seckill:applied_seq:{活动ID}` 决定一条消息能不能现在应用：

- 序号已经应用过：丢掉，避免重复消费写成两张券。
- 序号正好是下一个：调用 `apply`，再把 `applied_seq` 更新成这个序号。
- 中间缺号：先按事件表里实际存在的行投影，表里没有的序号直接跳过（热路径 `INCR` 过、但 Persist 没写成事件时会出现 1 然后 5）。表里也还没有这条时，才放进 `seckill:buffer:{活动ID}`，等下一条按序事件或回放。补洞时不再走一遍「缺号」判断，避免同一条消息被缓冲到拖死消费线程。

同一条事件写 Redis 和 Elasticsearch 也不在一个事务里。`apply` 先写 Redis，再写 Elasticsearch，两次都成功才更新 `applied_seq`。

两边用的身份都是「活动 ID + 用户 ID」。Redis 里 `seckill:coupon:{活动ID}:{用户ID}` 已经存在就不再发新的券编号。Elasticsearch 用同一个文档编号覆盖。所以同一条事件投影两遍，仍然是一张券。

如果 Redis 写完、Elasticsearch 抛错，`applied_seq` 不会往前走。`KafkaSecKillEventConsumer` 把这条消息送进死信主题 `seckill.events.dlt` 并提交偏移，这条消息本身不会自动再投一次。同一活动的下一条事件发现序号对不上，会从事件表把缺口重放，把没写上的 Elasticsearch 文档补上。

如果这是该活动的最后一条事件，后面没有新事件来触发补洞，就要调用下面的回放接口，按账本再投影一遍。

Query 服务不消费 Kafka。它只读 Event 已经写好的 Redis 或 Elasticsearch。所以链路是：

```text
PostgreSQL 事件 → outbox → Kafka → EventProjector → Redis
                                                      ↑
浏览器 → nginx → Gateway → Query ————————————————————┘
```

`SeckillQueryRestController` 的三个 GET：

| 方法 | 路径 | 数据从哪来 |
|------|------|------------|
| `queryCurrent` | `GET /query/promotions` | Redis 中的活动 |
| `querySuccess` | `GET /query/coupons/{customerId}` | Redis 中该用户的券 |
| `search` | `GET /query/coupons/search` | Elasticsearch |

路径参数 `{customerId}` 用 `@PathVariable`。搜索的 `customerId`、`promotionId` 用 `@RequestParam`，因为它们出现在 `?` 后面，而且可以不传。

## 读模型持久化与 checkpoint

抢券很多时，如果 Redis 读模型整库丢了，再从 0 全量 replay 会很慢。本仓库在 Docker Compose 里做了两层防护：

1. **Redis AOF + 数据卷**（`docker-compose.yml` 里 `redis-data`）：重启后尽量把热路径和读模型键找回来，包括 `seckill:applied_seq` 和券 string。
2. **PostgreSQL 表 `projection_checkpoint`**：Event 服务每投影成功一条带序号的事件，除了写 Redis，还会 upsert 该活动的 `lastAppliedSeq`。进程启动时 `ReadModelCheckpointBootstrap` 会检查：若读模型键还在、但 Redis 序号落后于 checkpoint，就把 Redis 序号补对齐，避免误以为要从 0 重放。

Elasticsearch 在 Compose 里同样挂了 **`es-data` 卷**，索引文件落盘，和 Redis 读模型是同一类「投影副本」，权威数据仍在事件表。

读模型键也丢了时，checkpoint **不能**代替全量重建，必须 replay 事件表。

## 回放

读模型可以重建，因为事实在 PostgreSQL 的事件表里。`ReplayController` 提供：

```text
POST /admin/replay?promotionId=...&fromSeq=0
POST /admin/replay?promotionId=...&incremental=true
```

这个接口在 **Event 服务的 8084** 上，不经过 Gateway，nginx 也没有代理它。`fromSeq` 默认 0，表示从这条活动的开头**全量**重放。`incremental=true` 且 `fromSeq` 仍为 0 时，从 `max(Redis applied_seq, PostgreSQL checkpoint) + 1` 开始，只适合读模型还在、只需补后面几条事件的场景。`EventProjector.replay` 按序号把事件再投影一遍。

投影失败的消息会进入死信主题 `seckill.events.dlt`，见上一节。消费者在 `library/seckill-infra-kafka/.../KafkaSecKillEventConsumer.java`：`onEvent` 抛错时调用 `publishDlt`。这一批里已经投影或已经进死信的记录，在批末一次 `commitSync`。还没处理的记录不提交，进程中途停掉后会再次投递。

查询「我的券」时，Redis 先读顾客的集合，再用一次 `MGET` 取出这些券，而不是每张券单独 `GET`。键名没有变。
